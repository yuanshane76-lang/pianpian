# GitHub 私有协作配置

## 仓库与权限

建议仓库名为 `zhiyan-workbench`，可见性为 **Private**。仓库保存源码和开发文档，用户密钥、论文、文献库和免安装压缩包继续保留在本机。

维护者管理仓库、确认产品方向和合入；开发者接受邀请后在任务分支提交 PR。个人账号仓库邀请的是协作者，不需要共享账号或交出管理员身份。

本次电脑上已有的 GitHub CLI 账号配置为 `yuanshane76-lang`。实际创建前由脚本再次读取已认证账号；如果登录的是其他账号，脚本会停止，避免把项目放到错误账号下。

旧开发仓库的产品设想曾包含疑似密钥，因此旧历史只保留在本机。用于协作的干净仓库位于 `paperquay-share`，以脱敏后的稳定源码和本次协作配置建立新的初始提交。不要从旧仓库或过渡 worktree 推送旧历史；后续协作从干净仓库或 GitHub clone 开始。尚未完成的并行产品改动另行审核后提交为 PR。

## 首次配置

先完成 GitHub CLI 登录。这一步在你的浏览器中授权，不要把 GitHub Token 写入源码或发到聊天里：

```powershell
gh auth login --hostname github.com --git-protocol https --web
gh auth status --hostname github.com
```

然后在已经验证并提交的协作分支工作区执行：

```powershell
pwsh -File scripts/setup-github.ps1
```

如果 Git 报错显示它正在连接 `127.0.0.1` 的未启动代理，可只为本次 Git 子命令绕过代理：

```powershell
pwsh -File scripts/setup-github.ps1 -BypassGitProxy
```

该参数不修改全局或仓库的代理设置。网页和 GitHub CLI 的授权成功，不代表 Git 的独立代理配置一定可用。

脚本会检查工作区、账号、仓库可见性和现有远程地址，创建或连接私有仓库，并上传已提交的代码。第一次向空仓库发布稳定基线属于初始化；已有 `main` 的仓库使用协作分支和 PR，不覆盖远程主分支。

脚本不会上传未提交的产品改动。共享仓库中的 `origin` 配置对所有 Git worktree 生效，原开发工作区的未提交内容仍留在原处。

上传前会校验实际读取和推送地址，并检查当前分支历史中的常见凭据格式。质量检查固定到一个提交 SHA，提交或分支中途变化时停止；空库初始化原子地要求远程 `main` 不存在。

## 主分支保护

质量检查的稳定名称为 `Quality checks (Windows)`，配置见 `.github/workflows/quality.yml`。

对于支持私有仓库分支保护的套餐，脚本尝试设置：

- 必须经过 PR；
- 至少一人审查，新的提交使旧审查失效；
- 上述质量检查通过，且分支与 `main` 保持最新；
- 禁止强制推送和删除 `main`；
- 管理员也遵守规则。

GitHub Free 的私有仓库通常不能使用分支保护。脚本遇到套餐或权限限制时，会如实报告保护没有启用，保留仓库和源码。团队仍按 `AGENTS.md` 执行 PR 流程；不能把书面约定描述为平台已强制实施。

第一次质量检查在代码推送后启动。仓库所有者创建自己的 PR 时，需要另一位协作者审查；只有一个开发者时不要声称已经完成独立审查。

## 邀请开发者

登录仓库页面，在 **Settings → Collaborators → Add people** 中邀请对方的 GitHub 用户名。对方接受后，按 `CONTRIBUTING.md` 克隆和开发。

提交任务前先写 Issue，标明任务范围和文件归属。共享入口、全局样式、依赖锁文件和跨层协议由相关开发者协调，避免多人同时改同一个工作区。

## 真实服务密钥

GitHub 协作不需要把你的 MinerU 或 DeepSeek 密钥交给其他人。自动检查不需要这两种密钥。

你本机的真实服务验证可以复用已经通过桌面客户端加密保存的配置。其他开发者自行在客户端配置；即使将来确实需要团队共用额度，也应通过可控的后端服务管理权限和额度，不把共享密钥放进前端或 Git 仓库。
